1. Purpose and Scope of This Document
Prototype-2 defined what to build — the architecture, research hypotheses, and design intent. This document tells AI coding agents and developers HOW to build it. Every component below includes concrete implementation steps, the specific algorithms to use, the data structures to maintain, and the decision logic required.
This document is specifically focused on the two core technical problems that make financial reconciliation hard:
Fuzzy Matching — finding records that refer to the same real-world event even when field values differ due to typos, formatting, truncation, abbreviations, currency rounding, or naming variation.
Financial Reconciliation — determining whether a financial relationship (match, split, fee-adjusted, reversed, delayed) holds between one or more records, using accounting rules rather than similarity scores alone.
2. Fuzzy Matching — Concrete Implementation
2.1 What Fuzzy Matching Is and Why It Is Needed
In a Razorpay payment ecosystem, the same underlying transaction appears in multiple systems with different representations. A merchant's invoice may say "Amazon Web Services India Pvt Ltd" while the bank statement says "AMZNWEBSERVICES". The amount ₹12,456.00 in the ERP may appear as ₹12,455.72 in the gateway after currency rounding. An order ID "ORD-2024-001847" may appear as "1847" in a legacy system.
Fuzzy matching is the process of finding these pairs despite surface-level differences. It has three stages: (1) blocking to reduce the search space, (2) similarity scoring across multiple fields, and (3) threshold-based candidate selection.
2.2 Blocking — Reducing the Search Space
Blocking prevents O(n²) comparisons by grouping records that could plausibly match. An AI agent must generate blocking keys before comparing anything.
Implement the following blocking strategies in order of priority:
Exact transaction ID blocking: if both records share any common identifier (UPI ref, gateway order_id, bank UTR number), place them in the same block immediately. This is a hard match candidate.
Amount-window blocking: group records whose amounts fall within ±2% of each other OR within ±₹50 (whichever is larger). Amounts outside this window can never match on amounts alone and skip comparison.
Date-window blocking: group records within a ±3 calendar day window. Settlement typically lags payment by T+1 or T+2. Refunds and reversals may appear up to 7 days later.
Phonetic/token blocking: tokenise merchant/description fields (split on spaces, slashes, dashes), apply Soundex or DoubleMetaphone to each token, then group records sharing ≥1 matching token. This catches "HDFC Bank" vs "HDFC Bk".
Prefix blocking: use the first 4 characters of normalised merchant name as a blocking key for large datasets.
A record pair only proceeds to similarity scoring if it survives at least one blocking key. This typically reduces comparisons by 95-99%.

2.4 Similarity Scoring
After normalisation, compute a weighted similarity score across fields. The score is a number between 0 and 1.
2.4.1 Amount Similarity
Amount similarity is a hard constraint, not a soft score. Apply the following rule:
amount_sim = 1.0   if abs(a1 - a2) == 0
amount_sim = 0.95  if abs(a1 - a2) <= 1 (rounding difference)
amount_sim = 0.80  if abs(a1 - a2) / max(a1, a2) <= 0.005 (≤0.5% difference, likely FX)
amount_sim = 0     if abs(a1 - a2) / max(a1, a2) > 0.02 (>2% difference)
Note: if the difference equals a known fee amount (e.g., Razorpay 2% MDR), set amount_sim = 0.90 and flag as fee-adjusted candidate.
2.4.2 String Similarity for Names and Descriptions
Use three algorithms and take the maximum:
Jaro-Winkler similarity: good for short strings and typos. Weight: 0.4.
Token Set Ratio (from RapidFuzz): splits both strings into token sets and computes sorted token intersection ratio. Good for word-order differences ("Flipkart India" vs "India Flipkart"). Weight: 0.4.
Longest Common Subsequence ratio: LCS length / max(len1, len2). Good for abbreviated strings. Weight: 0.2.
name_sim = 0.4 * jaro_winkler(s1, s2) + 0.4 * token_set_ratio(s1, s2) + 0.2 * lcs_ratio(s1, s2)
2.4.3 Date Similarity
date_sim = 1.0   if |d1 - d2| == 0 days
date_sim = 0.9   if |d1 - d2| == 1 day (T+1 settlement)
date_sim = 0.75  if |d1 - d2| == 2-3 days (T+2/T+3 settlement)
date_sim = 0.5   if |d1 - d2| == 4-7 days (late settlement or reversal window)
date_sim = 0     if |d1 - d2| > 7 days
2.4.4 Reference ID Similarity
ref_sim = 1.0   if normalised IDs are identical
ref_sim = 0.9   if one ID is a suffix/prefix of the other (e.g., "1847" in "ORD-001847")
ref_sim = 0.0   otherwise (IDs that don't overlap mean different transactions)

3. Financial Reconciliation — Concrete Implementation
3.1 What Reconciliation Is and How It Differs from Matching
Fuzzy matching finds candidate pairs. Reconciliation verifies that the financial relationship between those records is valid according to accounting rules. A record pair can have a high similarity score but fail reconciliation (e.g., two invoices with the same amount but different GST treatments), or have a modest similarity score but pass reconciliation cleanly (e.g., a split payment where three transactions sum to one invoice).
From the research literature (Fardous 2026, Gosangi 2025), effective reconciliation requires checking four independent dimensions: pricing compliance, authorization integrity, temporal consistency, and adjustment behavior. All four must pass for a MATCHED decision.
3.2 Reconciliation Rule Engine
Implement a deterministic rule engine that the LLM investigation agent calls as a tool. The engine takes an evidence bundle and returns a structured pass/fail/warning result for each rule category.
3.2.1 Amount Conservation Rules (Pricing Compliance)
These rules check that amounts add up correctly. They must be computed with integer arithmetic in paise — never floating point.
Rule AC-1 (Exact Match): sum(source_amounts) == sum(destination_amounts). Pass if equal.
Rule AC-2 (Fee-Adjusted Match): sum(source) == sum(destination) + fee_amount, where fee_amount is retrieved from the versioned fee schedule for this merchant category, date, and payment method.
Rule AC-3 (GST-Adjusted Match): sum(source) == sum(destination) + gst_amount, where gst_amount = base_amount × applicable_rate (18% standard, 12% reduced, 0% exempt). The applicable rate must be looked up from the GST rule table by HSN/SAC code and date.
Rule AC-4 (Split Payment): multiple source records sum to one destination record. Verify: sum(source_1..n) == destination, where each source_i shares the same parent order_id.
Rule AC-5 (Reversal): source amount == reversal amount, reversal date is within refund window (typically 90 days), reversal references original transaction ID.
FAIL if: none of AC-1 through AC-5 passes
WARN if: AC-2 passes but fee rate deviates >5% from scheduled rate
PASS if: any rule passes with zero deviation
3.2.2 Authorization Integrity Rules
These rules verify that every transaction was processed through proper approval chains. From Fardous (2026), authorization integrity is the second strongest predictor of reconciliation effectiveness (β=0.29).
Rule AI-1: every adjustment, reversal, or refund has a valid approval_code field that resolves to an authorized operator in the system.
Rule AI-2: discount amounts do not exceed the merchant's approved discount_ceiling_pct for their category and tier.
Rule AI-3: the payment method matches the merchant's approved payment method list (e.g., some merchants are not enabled for UPI Credit).
Rule AI-4: international transactions have a valid FEMA category code and the amount does not exceed the merchant's LRS (Liberalised Remittance Scheme) limit.
FAIL if: any authorization field is missing or resolves to an unauthorized role
WARN if: authorization is present but the approver role is lower than required for this amount tier
3.2.3 Temporal Consistency Rules
Settlement timelines in India follow RBI-mandated T+1 settlement for most UPI and card transactions, with T+2 for certain NEFT-based settlements.
Rule TC-1: settlement_date - payment_date is within [0, max_settlement_lag] days where max_settlement_lag is 1 for UPI, 2 for cards, 3 for net banking.
Rule TC-2: for reversals, reversal_date - original_date is within [0, 90] days.
Rule TC-3: invoice_date <= payment_date (payment cannot precede invoice creation).
Rule TC-4: for recurring subscriptions, charge_date falls within ±2 days of the expected billing_cycle_date.
FAIL if: TC-1 or TC-3 fails (hard constraint)
WARN if: TC-1 is within extended window (e.g., T+5) due to bank holiday — check RBI holiday calendar
3.2.4 Adjustment Behavior Rules
Adjustments are high-risk. The Fardous (2026) research shows adjustment behavior monitoring explains 21% of variance in leakage detection effectiveness independently of pricing checks.
Rule AB-1: the same transaction_id has not been reversed more than once.
Rule AB-2: the total credits/refunds issued to a customer in a rolling 30-day window do not exceed 3× their average monthly spend.
Rule AB-3: credit notes have a valid reason_code and the reason_code is on the approved list (not a catch-all category like "other").
Rule AB-4: write-off amounts require a secondary approval if exceeding ₹10,000.
FAIL if: AB-1 fails (duplicate reversal is a definite error)
WARN if: AB-2 or AB-3 fires (investigate but do not auto-fail)

4. Investigation Agent — Tool Calls and Decision Logic
4.1 Agent Inputs
The agent receives an evidence bundle containing: the candidate pair(s) from fuzzy matching, their composite similarity score, rule engine results for all four rule categories, any warning messages from the rule engine, and the leakage_risk score.
4.2 Agent Decision Tree
Implement this exact decision tree. The agent follows it in order and stops at the first applicable branch:
Branch 1 (Auto-Match): composite_score ≥ 0.92 AND all AC rules pass AND all AI rules pass AND leakage_risk < 0.1. → Decision: MATCHED. No LLM call needed. Log evidence bundle and proceed.
Branch 2 (Hard Contradiction): any AC rule returns FAIL AND no override explanation exists. → Decision: EXCEPTION. Log the specific rule that failed and the numerical discrepancy.
Branch 3 (Investigation Required): composite_score 0.75-0.91 OR any rule returns WARN OR leakage_risk 0.1-0.3. → Call investigate() tool. LLM examines evidence bundle, selects next tool call, and runs up to 5 investigation steps.
Branch 4 (Uncertain — Budget Reached): investigation steps exhausted without resolution. → Decision: UNCERTAIN. Route to human review queue with full evidence bundle and unresolved questions.
Branch 5 (Low Confidence): composite_score < 0.75. → Decision: UNCERTAIN. Do not force a match.
4.3 LLM System Prompt for Investigation
When calling the LLM, use this structured system prompt (adapt as needed):
You are a financial reconciliation investigator for a Razorpay payment system.
You have access to: retrieve_candidates(), get_related_events(), run_financial_rules(),
  inspect_entity_graph(), search_source_history(), test_reconciliation_hypothesis().
Rules:
1. You may call at most 5 tools per case.
2. Every numerical claim must be verified by run_financial_rules(), not computed by you.
3. State your hypothesis before each tool call.
4. If you cannot reach a confident decision, output UNCERTAIN with unresolved questions.
5. Never declare MATCHED without citing at least one passing AC rule result.
6. Output must be a JSON object with: decision, confidence (0-1), cited_evidence[], unresolved[].

5.2 Evidence Bundle Structure
The investigation agent works only from evidence bundles. An evidence bundle is assembled by the retrieval layer before the agent is called:

candidate_scores: fuzzy match scores between each pair
rule_results: output of the rule engine for each rule category

entity_graph_context: merchant tier, category, historic match rate
anomaly_signals: leakage_risk score and which construct drove it
missing_fields: list of fields that were null in source records
prior_cases: any previous reconciliation decisions for this merchant/order

7. LLM Constraints — What the Agent Must Never Do
These are hard constraints enforced by the policy verifier. The LLM cannot override them:
Never compute financial totals independently. All arithmetic must go through run_financial_rules(). LLMs have floating-point reasoning errors that are unacceptable in accounting contexts.
Never declare MATCHED on amount similarity alone. A reference ID conflict or authorization failure must block the match.
Never invent evidence. If a field is missing from the evidence bundle, state it as missing. Do not assume what it would have been.
Never label a record as fraudulent from an anomaly score alone. Anomaly scores are inputs to investigation, not conclusions.
Never override a hard rule failure with natural language reasoning. "The amounts are close enough" is not a valid override for a rule that returned FAIL.
Never store or transmit raw financial data outside the evidence bundle. Privacy and audit requirements apply.

8.3 UPI-Specific Reconciliation
UPI transactions require special handling due to the three-party structure (payer, payee, NPCI):
Match on UTR (UPI Transaction Reference) first — this is a globally unique identifier assigned by NPCI.
If UTR is missing (common in older records), match on VPA (Virtual Payment Address) + amount + date window.
UPI mandate transactions (recurring) have a mandate_id; match recurring charges against the mandate record.
UPI Autopay reversals must reference the original mandate_id, not just the transaction amount.

Step 2: Implement blocking keys and the candidate generation loop (Section 2.2). Verify that blocking reduces the search space by >90% on synthetic data.
Step 3: Implement composite similarity scoring (Section 2.4). Test against the 15 benchmark scenarios (Section 6.1).
