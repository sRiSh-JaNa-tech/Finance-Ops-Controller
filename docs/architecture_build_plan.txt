AI FINANCE CONTROLLER: ARCHITECTURE AND BUILD PLAN

SUMMARY

Build Prototype-2 as an evidence-grounded financial reconciliation system. It combines deterministic financial controls, candidate retrieval, entity resolution, graph context, anomaly detection, and one bounded investigation agent.

The system classifies cases as MATCHED, EXCEPTION, or UNCERTAIN. The primary research contribution is evaluating whether tool-mediated investigation and calibrated abstention reduce costly false matches and improve discrepancy-cause diagnosis compared with Prototype-1 and non-agentic baselines.

ARCHITECTURE

Synthetic financial sources
        -> ingestion and schema validation
        -> canonical event/entity model with provenance
        -> indexes, blocking, embeddings, and entity graph
        -> candidate relationships and computed findings
        -> evidence bundle builder
        -> Investigation Agent
             - retrieve_candidates()
             - get_related_events()
             - run_financial_rules()
             - inspect_entity_graph()
             - search_source_history()
             - test_reconciliation_hypothesis()
        -> deterministic policy verifier
        -> calibrated decision
        -> audit record and human-review queue

CORE COMPONENTS

1. Synthetic data generator

Generate bank, payment-gateway, invoice, accounting, settlement, customer, and merchant records.

Include clean matches, duplicates, missing records, delayed settlement, fees, taxes, refunds, reversals, partial payments, split payments, currency conversion, time-zone differences, corrupted identifiers, spelling variations, ambiguous candidates, and suspicious patterns.

Every record must retain a hidden ground-truth transaction or event identifier.

2. Canonical data model

Normalize all sources into shared transaction, entity, payment, invoice, and settlement-event structures.

Preserve original source values, normalized values, source system and record ID, transformation history, timestamps, currency, amount, fee, tax, net amount, customer and merchant references, invoice and payment references, reversal/refund status, settlement relationships, and field-level provenance.

3. Retrieval and matching layer

Use a staged approach:

- Exact trusted identifiers.
- Blocking by amount, date window, currency, merchant, and references.
- Lexical and fuzzy matching.
- Embedding similarity.
- Entity-graph context.
- Constraint-aware one-to-many matching.

The LLM must never search all records directly. It receives only bounded candidate sets and verified evidence.

4. Deterministic financial controls

Implement versioned rules for amount conservation, fee and tax adjustments, currency compatibility and conversion, transaction and settlement date windows, partial captures, split payments, refunds, reversals, duplicate settlement, missing or extra records, and effective-dated settlement policies.

Deterministic rules are authoritative for numerical and accounting decisions.

5. Investigation agent

Use one bounded agent rather than eight loosely autonomous agents.

The agent may form reconciliation hypotheses, select permitted evidence-retrieval tools, interpret noisy descriptions and references, compare competing explanations, identify missing or contradictory evidence, decide when investigation should stop, and produce a structured recommendation with citations.

The agent may not alter source data, invent records, perform authoritative calculations, override hard financial contradictions, or issue an uncited final match.

6. Evidence bundle

Each investigation receives an immutable evidence bundle containing source record identifiers, relevant original and normalized fields, candidate scores, rule results and rule versions, amount/date/currency comparisons, entity-graph paths, related events, anomaly signals, missing fields, contradictions, and previous investigation results.

Every explanation must be generated from this bundle.

7. Decision and abstention policy

MATCHED requires a unique relationship, all mandatory controls passing, no unresolved contradiction, and risk below the automatic-match threshold.

EXCEPTION requires a verified contradiction such as an unexplained imbalance, duplicate settlement, invalid reversal, or confirmed missing/extra record.

UNCERTAIN applies when evidence is incomplete, candidates are tied, the investigation budget is exhausted, source data is unavailable, or false-match risk is too high.

Automatic matching must use a stricter threshold than exception detection. Suspicion alone must not be labeled fraud.

8. Human-review workflow

Escalate high-materiality cases, ambiguous candidates, contradictory identifiers, missing sources, unseen transaction types, and cases exceeding the investigation budget.

Reviewers must see the evidence bundle, hypotheses, tool calls, rule results, proposed outcome, and unresolved questions. Their decision is stored as additional labeled data without modifying the original audit record.

BUILD PHASES

1. Define schemas, event relationships, provenance fields, decision labels, and reason labels.
2. Build the synthetic generator and hidden transaction graph.
3. Implement ingestion, normalization, validation, and audit-preserving storage.
4. Implement blocking, retrieval, fuzzy matching, embeddings, and graph lookup.
5. Implement versioned financial rules and one-to-many reconciliation constraints.
6. Build the evidence bundle and typed investigation tools.
7. Implement the bounded investigation agent and stopping policy.
8. Add policy verification, calibration, structured explanations, and human-review output.
9. Implement baselines and ablations.
10. Run repeated-seed evaluation on held-out error templates.

EVALUATION

Required baselines:

- Exact identifier matching
- Deterministic rule matching
- Fuzzy lexical matching
- Embedding retrieval
- Classical machine-learning linkage
- Raw pairwise LLM matching
- LLM with retrieved candidates
- Prototype-1 hybrid pipeline
- Prototype-2 investigation agent

Required ablations:

- No graph context
- No embeddings
- No financial rules
- No additional tool calls
- No abstention
- One-pass evidence summarizer
- No structured evidence validation
- Different investigation budgets

Measure match precision, recall, and F1; false-match rate; exception precision and recall; cause-diagnosis accuracy; one-to-many amount consistency; coverage and selective risk; calibration error and Brier score; abstention quality; automation and review rates; tool-call count; latency; token usage; cost; throughput; evidence citation validity; numerical and rule-claim correctness; and auditor reproducibility.

Use a cost-weighted objective where false automatic matches cost substantially more than missed matches or human reviews.

ACCEPTANCE CRITERIA

The prototype must:

- Automatically reconcile clean and clearly fee-adjusted records.
- Correctly investigate delayed settlements, refunds, reversals, and split payments.
- Abstain on tied candidates, missing evidence, contradictory records, and unseen transaction types.
- Preserve source data and field-level provenance.
- Produce structured, verifiable evidence for every decision.
- Demonstrate lower cost-weighted false-match risk than Prototype-1 or raw LLM matching.
- Report results by scenario and held-out error template, not only aggregate accuracy.
- Log every agent tool call and stopping decision.

ASSUMPTIONS AND BOUNDARIES

- The implementation initially uses synthetic data only.
- The file named prototype-2 is the intended Prototype-2 source file despite lacking a .txt extension.
- Production privacy, regulatory compliance, access control, and real-bank integration remain outside this prototype.
- The system is an AI-assisted financial verification tool, not a replacement for accounting controls or human oversight.
