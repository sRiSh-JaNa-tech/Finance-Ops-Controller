1. EXECUTIVE SUMMARY & SCIENTIFIC NOVELTY
--------------------------------------------------------------------------------
Financial transaction reconciliation across fragmented platforms (payment gateways,
banking networks, ERP ledgers, GST tax systems) has historically been split between:
  (a) Rigid, brittle deterministic rule scripts that fail under minor field mutations,
  (b) Uncalibrated machine learning / heuristic pairwise classifiers that suffer from
      high false-positive rates and lack accounting guarantees.

Prototype 3 bridges this gap by implementing an Evidence-Grounded Autonomous
Investigation Agent powered by Google Gemini on Vertex AI. The architecture separates
probabilistic evidence retrieval from deterministic accounting verification:
  - Probabilistic and AI layers generate candidates, identify missing facts, and
    formulate diagnostic hypotheses over multi-party transaction graphs.
  - Deterministic accounting kernels enforce integer-arithmetic conservation (paise),
    statutory GST schedules, RBI settlement timelines, and authorization integrity.
  - Gemini Vertex AI orchestrates a 5-Stage ReAct (Reason + Act) cognitive state machine
    using native Vertex AI Tool/Function Calling to iteratively investigate ambiguous
    cases, quantify revenue leakage, and output calibrated Match, Exception, or
    Abstention (Uncertain/Human-in-the-loop) decisions with 100% audit provenance.

3. CANONICAL LEDGER DATA MODEL & INGESTION SPECIFICATION
--------------------------------------------------------------------------------
3.1 Integer Paise Quantization
All monetary values MUST be stored and computed as signed 64-bit integers in Indian
Paise (1 INR = 100 Paise). Floating-point representations for amounts are strictly
prohibited in accounting kernels to prevent IEEE-754 rounding inaccuracies.

3.2 Canonical Transaction Schema (Vallemoni 2021)
Every record ingested from Bank Statements, Payment Gateways (Razorpay), ERP Systems,
or GST Portals is lifted into the following canonical schema:

  Field Name          Type             Description / Validation Rule
  ---------------------------------------------------------------------------------------
  txn_id              UUID4 (str)      System-generated globally unique transaction ID
  source_system       Enum             BANK | RAZORPAY | ERP | GST | MERCHANT_PORTAL
  source_id           String           Original identifier in source system
  amount_paise        Integer (int64)  Gross transaction amount in Paise (e.g., 123450 = ₹1,234.50)
  fee_paise           Integer (int64)  Gateway/Platform processing fee in Paise
  gst_paise           Integer (int64)  Goods & Services Tax in Paise (18% on fee standard)
  net_paise           Integer (int64)  Net settled amount: amount_paise - fee_paise - gst_paise
  currency            String(3)        ISO 4217 code (INR, USD, EUR). Default: INR
  txn_timestamp       Integer (int64)  UTC epoch timestamp of transaction initiation
  settlement_timestamp Integer (int64) UTC epoch timestamp of funds settlement (or None)
  merchant_id         String           Unique merchant identifier
  merchant_name_raw   String           Raw merchant name as received
  merchant_name_norm  String           Normalized merchant string (lowercase, stripped, expanded)
  counterparty_name   String           Payer / Beneficiary name
  payment_method      Enum             UPI | CARD | NETBANKING | WALLET | EMI | NA
  status              Enum             CAPTURED | REFUNDED | FAILED | REVERSED | PENDING
  parent_txn_id       Optional[str]    For refunds/reversals: source_id of parent transaction
  order_id            Optional[str]    Merchant order reference ID
  invoice_ref         Optional[str]    ERP invoice reference identifier
  utr                 Optional[str]    NPCI UPI Transaction Reference (12 digits) / Bank UTR
  vpa                 Optional[str]    UPI Virtual Payment Address (e.g., user@okhdfcbank)
  gstin               Optional[str]    15-character GST identification number
  approval_code       Optional[str]    Bank authorization approval code
  reason_code         Optional[str]    Adjustment / Refund reason code
  provenance          Dict[str, Any]   Full lineage: raw source payload, ingestion timestamp,
                                       transformation hash, pipeline version.

3.3 Ingestion Normalization Rules (Furche et al. 2016)
  1. Amount Normalization:
     - Regex strip `[₹$,\s]`.
     - Parse decimal string `D` to exact Paise: `amount_paise = int(round(Decimal(D) * 100))`.
  2. Merchant Name Normalization:
     - Convert to ASCII lowercase. Remove special characters `[^\w\s]`.
     - Expand standard abbreviations via lookup:
       `{"pvt": "private", "ltd": "limited", "bk": "bank", "co": "company", "corp": "corporation", "tech": "technology", "in": "india"}`.
     - Collapse multiple whitespaces.
  3. Date & Timestamp Normalization:
     - Parse multi-format strings (`DD-MM-YYYY`, `YYYY-MM-DDTHH:MM:SSZ`, `DD/MM/YY`) to UTC epoch integer.
     - Default unspecified time to `00:00:00 UTC`.
  4. Reference Identifier Normalization:
     - Remove prefixes (`ORD-`, `INV-`, `UPI-`, `REF-`), dashes, spaces, and leading zeros.
     - Convert to uppercase alphanumeric.
  5. Currency Normalization:
     - Map symbols `{"₹": "INR", "Rs": "INR", "$": "USD", "€": "EUR"}` to ISO 4217.

4. SEARCH SPACE PRUNING: MULTI-PASS BLOCKING & PROGRESSIVE SCHEDULING
--------------------------------------------------------------------------------
To prevent O(N * M) quadratic comparison complexity over high-volume transaction
streams, the system implements multi-pass blocking (Papadakis 2012) combined with
cost-benefit prioritized partition scheduling (Sun et al. 2022).

4.1 Multi-Pass Blocking Keys (Papadakis 2012)
Candidate pairs (A in System 1, B in System 2) are generated if they share AT LEAST ONE
blocking key from the following ordered hierarchy:

  Key ID   Key Name                   Generation Logic
  ---------------------------------------------------------------------------------------
  K_1      Exact Reference Block      Match on exact normalized UTR, order_id, or invoice_ref.
  K_2      Windowed Amount Block      Group by amount bucket: floor(amount_paise / 5000)
                                      (Checks current bucket and adjacent +/- 1 bucket).
  K_3      Windowed Date Block        Group by calendar day: floor(txn_timestamp / 86400)
                                      (Checks +/- 3 calendar days for settlement lag).
  K_4      Phonetic Token Block       Tokenize normalized merchant name, apply DoubleMetaphone
                                      or Soundex to each token. Group by (token_soundex, amount_bucket).
  K_5      Prefix Block               First 4 characters of normalized merchant name + date_bucket.

4.2 Progressive Block Scheduling (Sun et al. 2022)
Blocks are scheduled dynamically based on estimated match density (Cost-Benefit Ratio):
  Benefit(B) = Estimated High-Confidence Matches in Block B
  Cost(B) = |Records_A in B| * |Records_B in B|
  Priority(B) = Benefit(B) / Cost(B)
Blocks with exact reference keys (K_1) have Priority ~ 1.0 and are evaluated first,
achieving progressive resolution where >80% of matches are found in the first 10% of
compute time. Target Reduction Ratio: RR >= 95.0%.

5. HYBRID GENERALIZED ENTITY MATCHING & SIMILARITY METRIC SCORING
--------------------------------------------------------------------------------
Surviving candidate pairs (A, B) are evaluated across 4 dimensional similarity kernels,
synthesized into a composite score (Zabolotnia & Kozynets 2025; Wang et al. 2022).

5.1 Amount Similarity Kernel (S_amt)
Amount equality is evaluated with integer tolerance and fee schedule awareness:
  - If A.amount_paise == B.amount_paise:
      S_amt = 1.00
  - If abs(A.amount_paise - B.amount_paise) <= 100 (<= ₹1.00 rounding tolerance):
      S_amt = 0.95
  - If abs(A.amount_paise - B.amount_paise) / max(A.amount_paise, B.amount_paise) <= 0.005 (<= 0.5% FX):
      S_amt = 0.85
  - If diff matches known fee rate (e.g. 2.0% MDR -> diff == round(0.02 * A.amount_paise)):
      S_amt = 0.90 (Flagged as Fee-Adjusted Candidate)
  - If diff > 2.0% and diff does not match scheduled fee/GST:
      S_amt = 0.00

5.2 Reference Identifier Similarity Kernel (S_ref)
  - If A.clean_ref == B.clean_ref and len(A.clean_ref) >= 4:
      S_ref = 1.00
  - If A.clean_ref is suffix/prefix of B.clean_ref (e.g., "1847" vs "001847"):
      S_ref = 0.90
  - If both records have non-empty references that completely diverge:
      S_ref = 0.00
  - If one or both references are missing (null):
      S_ref = 0.50 (Neutral signal; does not reward or penalize)

5.3 Hybrid String Similarity Kernel (S_name)
For merchant and narrative text, compute three complementary metrics (Zabolotnia 2025):
  1. Jaro-Winkler (JW): Typo tolerance on short tokens.
  2. Token Set Ratio (TSR): Invariance to word reordering and token subsets.
  3. Longest Common Subsequence (LCS): Invariance to abbreviations and concatenations.
  Formula:
    S_name = 0.40 * JW(name_A, name_B) + 0.40 * TSR(name_A, name_B) + 0.20 * LCS_Ratio(name_A, name_B)

5.4 Date Temporal Decay Kernel (S_date)
Let Delta_Days = abs(A.txn_timestamp - B.txn_timestamp) / 86400.0:
  - Delta_Days <= 0.5: S_date = 1.00 (Same day)
  - Delta_Days <= 1.5: S_date = 0.90 (T+1 RBI UPI/Card settlement)
  - Delta_Days <= 3.5: S_date = 0.75 (T+2/T+3 NEFT/Bank settlement)
  - Delta_Days <= 7.5: S_date = 0.50 (Late presentment / weekend / holiday)
  - Delta_Days > 7.5:  S_date = max(0.0, 0.50 - 0.05 * (Delta_Days - 7.5))

5.5 Composite Similarity Score & Hard Constraint
Weights tailored for Indian multi-party financial payment reconciliation:
  Composite_Score = 0.40 * S_amt + 0.30 * S_ref + 0.15 * S_name + 0.15 * S_date

CRITICAL HARD CONSTRAINT (Smith et al. 2025):
  If S_amt == 0.0 AND S_ref == 0.0:
      Composite_Score = 0.00
  (Rationale: Two records with completely unaligned amounts and conflicting explicit
   references cannot represent the same financial transaction, regardless of name similarity).

6. DETERMINISTIC FINANCIAL RULE ENGINE & REVENUE LEAKAGE DETECTION
--------------------------------------------------------------------------------
6.1 17 Deterministic Financial Audit Rules (Ikponmwoba 2024; Vallemoni 2021)
The rule engine executes 17 domain-specific accounting rules grouped into 4 categories.
Every rule executes via exact integer arithmetic and returns PASS, WARN, or FAIL with
numerical proofs.

[Category 1: Amount Conservation / Pricing Compliance (AC)]
  AC-1: Exact Match
        Condition: sum(A.amount_paise) == sum(B.amount_paise)
  AC-2: Fee-Adjusted Match
        Condition: A.amount_paise == B.amount_paise + B.fee_paise, where fee_paise is
        verified against the effective-dated merchant pricing contract.
  AC-3: GST-Adjusted Match
        Condition: B.gst_paise == round(B.fee_paise * applicable_gst_rate) (18% standard).
  AC-4: Split Payment Aggregation
        Condition: sum(A_1..n.amount_paise) == B.amount_paise, where all A_i share order_id.
  AC-5: Reversal / Refund Conservation
        Condition: A.amount_paise == Refund.amount_paise AND Refund.timestamp >= A.timestamp.

[Category 2: Authorization Integrity (AI)]
  AI-1: Approval Code Verification
        Condition: Refund/Reversal/Adjustment has a valid cryptographic approval_code.
  AI-2: Merchant Discount Ceiling Check
        Condition: Applied discount <= merchant_tier_discount_ceiling.
  AI-3: Authorized Payment Method
        Condition: Transaction payment_method is enabled on merchant profile.
  AI-4: Cross-Border & FEMA Compliance
        Condition: If currency != 'INR', valid FEMA category code and LRS limit checked.

[Category 3: Temporal Consistency (TC)]
  TC-1: Settlement Lag Window
        Condition: (settlement_ts - txn_ts) <= max_allowed_lag (UPI=1d, Card=2d, NetBanking=3d).
  TC-2: Statutory Refund Window
        Condition: (refund_ts - original_ts) <= 90 calendar days.
  TC-3: Chronological Causality
        Condition: invoice_timestamp <= payment_timestamp.
  TC-4: Recurring Subscription Interval
        Condition: charge_ts is within +/- 2 days of expected billing_cycle_ts.

[Category 4: Adjustment Behavior Monitoring (AB)]
  AB-1: Unique Reversal Integrity
        Condition: Count of refunds/reversals referencing parent_txn_id <= 1 (Zero double refunds).
  AB-2: Velocity & Volume Leakage Monitor
        Condition: Rolling 30-day customer refund total <= 3x average monthly spend.
  AB-3: Structured Reason Code Enforcement
        Condition: reason_code in approved taxonomy (excludes generic "OTHER").
  AB-4: High-Value Write-Off Authorization
        Condition: If write_off_paise > 1000000 (₹10,000), secondary supervisor approval present.

6.2 Empirical Revenue Leakage Score (Fardous 2026)
Following Fardous (2026), four empirical constructs are evaluated on a [0.0, 1.0] scale:
  - PCD  = Pricing Compliance Score (AC rules pass rate)
  - AI   = Authorization Integrity Score (AI rules pass rate)
  - ABM  = Adjustment Behavior Score (AB rules pass rate)
  - TAI  = Temporal Anomaly Score (TC rules pass rate)

Standardized regression equation (Fardous 2026, R^2 = 0.62, p < 0.001):
  Leakage_Risk = 1.0 - (0.38 * PCD + 0.29 * AI + 0.21 * ABM + 0.17 * TAI)

Decision Trigger:
  - If Leakage_Risk < 0.10: Low risk / Clean transaction.
  - If 0.10 <= Leakage_Risk <= 0.30: Moderate risk; triggers Agent Investigation.
  - If Leakage_Risk > 0.30: High risk of revenue leakage / financial discrepancy.

7. GEMINI VERTEX AI INVESTIGATION AGENT & COGNITIVE THINKING PROTOCOL
--------------------------------------------------------------------------------
When cases exhibit ambiguity, discrepancy, or moderate-to-high leakage risk, they are
dispatched to the Gemini Vertex AI Investigation Agent.

7.1 Fast-Path Decision Gating
Before invoking LLM API calls, the system executes deterministic fast-path gating:
  - AUTO-MATCH Gate:
    If Composite_Score >= 0.92 AND all AC rules PASS AND all AI rules PASS AND Leakage_Risk < 0.10:
    -> Decision: MATCHED (0 tool calls, zero token cost).
  - AUTO-EXCEPTION Gate:
    If Hard AC rule FAILS (e.g. unexplained amount difference > 2%) AND no split/reversal pattern:
    -> Decision: EXCEPTION (0 tool calls, immediate deterministic rejection).
  - INVESTIGATION Gate:
    If 0.75 <= Composite_Score < 0.92 OR any rule returns WARN OR 0.10 <= Leakage_Risk <= 0.30:
    -> Invoke Gemini Vertex AI Investigation Agent.

7.2 Gemini Vertex AI Integration Specs
  - SDK Support: Google Cloud Vertex AI (`google.cloud.aiplatform` / `vertexai`) & `google-genai`.
  - Model Targets: `gemini-2.5-flash-lite` (default), `gemini-2.0-flash`, `gemini-1.5-pro`, `gemini-1.5-flash`.
  - API Credentials: Application Default Credentials (ADC), `GOOGLE_APPLICATION_CREDENTIALS`,

7.4 5-Stage ReAct Cognitive Thinking Loop (Liu 2025; Fu et al. 2025)
When investigating a case, the agent executes up to 5 iterative cognitive cycles:

  STAGE 1: OBSERVE
    Load compact Evidence Bundle: Source transaction, candidate records, initial similarity
    scores, deterministic rule results, and leakage signals.

  STAGE 2: HYPOTHESIZE
    Formulate explicit competing hypotheses with calibrated prior probabilities:
      H_1: EXACT_MATCH
      H_2: FEE_ADJUSTMENT (Gateway MDR deduction)
      H_3: SPLIT_PAYMENT (Multiple payments for single invoice)
      H_4: DELAYED_SETTLEMENT (Bank holiday / weekend lag)
      H_5: DUPLICATE_OR_REVERSAL (Double credit or legitimate refund)
      H_6: REVENUE_LEAKAGE (Unauthorized adjustment or fee divergence)
      H_7: AMBIGUOUS (Insufficient evidence / unresolvable tie)

  STAGE 3: SELECT TOOL (Information-Gain Maximization)
    Emit a Vertex AI function call targeting the tool that will maximally eliminate
    hypothesis entropy. Maximum tool budget per case: k = 5.

  STAGE 4: SYNTHESIZE
    Process tool execution payload. Refute invalidated hypotheses, recalculate posterior
    probabilities for surviving hypotheses, and update the evidence bundle.

  STAGE 5: CONVERGE (Stopping Policy)
    - If Posterior(H_best) >= 0.85 AND required deterministic accounting rules PASS:
        Emit definitive decision: MATCHED or EXCEPTION.
    - If Tool Budget Exhausted OR Evidence remains conflicting/under-specified:
        Emit calibrated UNCERTAIN (Abstain) with itemized unresolved questions for human auditor.

8. HARD CONSTRAINTS, POLICY VERIFIER & AUDITABLE EVIDENCE RECORDS
--------------------------------------------------------------------------------
8.1 Policy Verifier Hard Constraints (Zero-Hallucination Protocol)
The system wraps all AI decisions in a deterministic Policy Verifier that enforces:
  1. No Arithmetic Hallucination: The agent is forbidden from asserting mathematical
     equality; all sums and fee equations must be backed by a passing `run_financial_rules`
     or `test_reconciliation_hypothesis` execution record.
  2. No Match Without AC Rule: Under no circumstance can a decision be MATCHED unless
     at least one Amount Conservation rule (AC-1, AC-2, AC-3, AC-4, AC-5) returned PASS.
  3. No Natural Language Override of Hard Failures: An LLM stating "The discrepancy is
     negligible" cannot override a rule returning FAIL.
  4. Evidence Provenance Integrity: Every cited record ID in `cited_evidence` must exist
     in the ingested database.
  5. Calibrated Abstention: If confidence < 0.75 or tie between top candidates (score
     diff < 0.05), the decision MUST be UNCERTAIN.

Every case outputs an immutable, standards-compliant JSON audit record:

10. STANDARDS-COMPLIANT EVALUATION PROTOCOL (PyResolveMetrics)
--------------------------------------------------------------------------------
Evaluation follows PyResolveMetrics standards (Olar & Diosan 2024; Lopes 2026):

10.1 Primary Metrics:
  - Pairwise Precision (P): TP / (TP + FP)
  - Pairwise Recall (R): TP / (TP + FN)
  - Pairwise F1-Score: 2 * P * R / (P + R)
  - Reduction Ratio (RR): 1.0 - (Candidate Pairs Generated / Total Cartesian Product)
  - Pairs Completeness (PC): True Matches in Candidate Set / Total True Matches in Ground Truth
  - False Match Rate (FMR): False MATCHED Decisions / Total MATCHED Decisions (Target: FMR < 0.5%)
  - Selective Prediction Risk-Coverage Curve: Accuracy vs Coverage as abstention threshold varies.
  - Asymmetric Financial Cost Function:
      Cost = 10 * Count(False_Matches) + 1 * Count(False_Exceptions) + 0.5 * Count(Uncertain_Escalations)
  - Tool Efficiency: Average tool calls per resolved case (Target: < 2.5).
